### 0.2 P5 的边界：没有改什么

读增量之前先划清边界，避免把旧链路当成 P5 新代码：

- **生成链路没改**：Prompt 组装、空回答检查、DeepSeek 流式仍走 P1/P2；P5 只在流结束时读 usage 并记一条用量
- **重排没改**：仍是「宽召回 → 重排 → top-k」；P5 只是把重排候选来源从纯 dense 换成 dense+sparse 融合结果
- **会话与消息表结构没重写**：只给 `Conversation` 加 `KnowledgeBaseScopeJson` / `ScopeAll`，消息与引用结构不变
- **权限模型没改**：仍是 P3 的「系统角色 + 知识库成员」；P5 只是逐库调用同一个 `KnowledgeBaseAccessChecker`
- **前端没有引入路由**：仍是 `App.vue` 内组件切换；检索设置是 Pinia + localStorage，不进后端配置
- **没有做**：按库配置权重、HyDE、Jieba、多租户隔离、开放 API、URL 抓取、OCR

### 1.1 两个迁移

| 迁移 | 表 | 变更 | 服务于 |
|---|---|---|---|
| `20261027051956_P5_ConversationScope` | `AppConversations` | 新增 `KnowledgeBaseScopeJson`（JSON 数组）、`ScopeAll` | T4 |

`AiUsageRecord` 继承 `CreationAuditedAggregateRoot<Guid>`：用量只追加、不修改，创建时间直接作为按天聚合的维度。

### 1.2 Qdrant schema：一个 collection，两种向量

`knowvault_chunks` 从 P4 的「一个 unnamed dense」升级为：

- **unnamed dense**：1024 维 Cosine，语义召回，payload 与旧版一致
- **named sparse `text`**：`Modifier.Idf`，关键词召回；文档侧 `1 + ln(tf)`，查询侧每个唯一词元 1.0

稀疏向量不能 PATCH 到既有 collection，所以 P4 → P5 必须重建。检测与重建分别在：

- `src/KnowVault.EntityFrameworkCore/VectorStore/QdrantVectorStore.cs:34` `EnsureCollectionAsync`：读 collection 配置，缺少 `text` 时抛 `VectorSchemaMismatchException`
- `src/KnowVault.EntityFrameworkCore/VectorStore/QdrantVectorStore.cs:153` `RecreateCollectionAsync`：删除并按新 schema 重建（含 payload 索引）
- `src/KnowVault.Ingest/Processing/QdrantCollectionInitializer.cs:30`：启动时捕获该异常，只记日志不阻断应用启动
- `src/KnowVault.Application/Maintenance/MaintenanceAppService.cs:41` `RebuildVectorIndexAsync`：重建 collection → 枚举 Ready 文档逐篇 `ReprocessAsync` → 返回 `RequeuedCount` / `SkippedCount`

维护入口是 Admin 接口 `POST /api/app/maintenance/rebuild-vector-index`，没有自动迁移。

## 2. 检索链路（读这一段就够）

### 2.1 总入口

`src/KnowVault.Ai/Rag/RagService.cs:107` `RetrieveAsync` 是唯一编排点：

1. 解析 `topK`（1–8）与重排候选数（默认 20，上限 100）
2. 合并请求级开关：`HybridEnabled` / `RewriteEnabled` 优先，其次全局配置
3. 查询列表永远以原问题开头；改写开启时追加变体
4. 走混合还是纯向量：`hybridEnabled || queries.Count > 1`，否则走 `RetrieveDenseAsync`（P4 行为）
5. 融合结果直接进 `RerankAsync`，重排只打分，本地取前 topK

### 2.2 混合召回与 RRF

`src/KnowVault.Ai/Rag/RagService.cs:182` `RetrieveHybridAsync`：

- 一次批量 embedding，多个查询共享
- 每个查询分别产生 dense 分支与 sparse 分支；改写变体整条查询乘 `VariantWeight`（默认 0.8）
- 问题切不出词元（全是停用词 / 标点）时跳过 sparse 分支
- sparse 抛错时记 warning 并把 `sparseAvailable` 置 false，后续查询只走 dense；已产生的 dense 分支继续融合
- 分支为空时返回空列表，不抛错

`src/KnowVault.Ai/Retrieval/ReciprocalRankFusion.cs:14`：

- 只使用排名：`weight × queryWeight / (RrfK + rank)`，默认 `RrfK=60`
- 同一分支内重复 ID 只算首次排名，防止人为放大
- 排序依次比较融合分、最佳排名、ID，保证结果可重复

### 2.3 重排与降级

`src/KnowVault.Ai/Rag/RagService.cs:373`：沿用 P2 的「失败退回原顺序」，P5 只把入参换成融合候选。引用分数在重排开启时是重排分，关闭时是 RRF 分，不跨问题比较。

### 2.4 查询改写

`src/KnowVault.Ai/Rag/RagService.cs:282` `TryRewriteAsync`：

- `MaxVariants` 上限强制 2；问题长度小于 `MinQuestionLength`（默认 6）直接跳过
- 调 `QueryRewriteService` 一次非流式请求，`temperature=0`、`max_tokens=200`
- 返回结果截断到 `MaxVariants`，任何异常只记 warning 并返回空列表
- 改写本身的 token 与耗时按 `AiOperationEnum.QueryRewrite` 记用量

**对外契约**：`RetrieveAsync` 返回的 `RewriteQueries` 原问题在第一位（内部融合需要）；`AnswerStreamAsync` 用 `Skip(1)` 只把变体放进 `RagStreamResult.RewriteQueries`（`src/KnowVault.Ai/Rag/RagService.cs:101`），所以 Started 帧与前端只看到变体，不重复显示原问题。

## 3. 稀疏索引链路

### 3.1 切词与哈希

- `src/KnowVault.Domain/Search/KeywordTokenizer.cs:15`：NFKC → 小写 → 按字符类别切段；CJK 连续片段取**重叠二元组**（单字保留），拉丁/数字连续片段长度 ≥ 2
- `src/KnowVault.Domain/Search/KeywordStopWords.cs`：内置最小停用词，只过滤整词元
- `src/KnowVault.Domain/Search/SparseVectorBuilder.cs:15` `BuildDocument`：文档侧 `1 + ln(tf)`，索引文本是 `HeadingPath + "\n" + Content`
- `src/KnowVault.Domain/Search/SparseVectorBuilder.cs:35` `BuildQuery`：查询侧每个唯一词元 1.0；切不出词元返回 null
- `src/KnowVault.Domain/Search/SparseVectorBuilder.cs:53` `HashToken`：FNV-1a 32 位，映射到 `1..uint.MaxValue-1`；禁止 `string.GetHashCode()`

### 3.2 写入与查询

- 写入：`src/KnowVault.Ingest/Processing/DocumentProcessor.cs:149` 为每个切片同时构造 dense 与 sparse，一次 `UpsertAsync`
- dense 查询：`QdrantVectorStore.SearchAsync`（新版 Query API）
- sparse 查询：`src/KnowVault.EntityFrameworkCore/VectorStore/QdrantVectorStore.cs:110`，`usingVector = "text"`，payload 与 dense 相同
- 评估用全量滚动：`QdrantVectorStore.ScrollAsync`，只给 `tools/KnowVault.Eval` 解析锚点

### 3.3 重建顺序

1. Admin 调 `POST /api/app/maintenance/rebuild-vector-index`
2. collection 删除并按新 schema 重建（`RecreateCollectionAsync`）
3. 所有 `Ready` 文档逐篇重新入队；`Processing` 跳过并计入 `SkippedCount`
4. 等文档重新处理完成后再问答；处理中的文档不会自动补跑

## 4. 用量与成本链路

### 4.1 记录

`src/KnowVault.EntityFrameworkCore/Ai/AiUsageRecorder.cs:45`：

- 每次记录独立 `requiresNew` UoW，写失败只 warning
- `TotalTokens = PromptTokens + CompletionTokens`，费用按 `AiOperationEnum` 选择单价，写入时固化 `EstimatedCostCny`
- 没有真实 usage 时按字符数估算，并置 `IsEstimated=true`

记录点全部在 `RagService`：

| 操作 | 位置 | Token 来源 |
|---|---|---|
| Embedding | `EmbedAsync`（`RagService.cs:417`） | embedding 响应 usage，缺失时估算 |
| Rerank | `RerankAsync`（`RagService.cs:373`） | rerank `TotalTokens` |
| QueryRewrite | `TryRewriteAsync`（`RagService.cs:282`） | 响应 usage，缺失时估算 |
| Chat | `StreamWithEmptyCheckAsync`（`RagService.cs:329`） | 流末 usage，缺失时估算 |

摄取侧 embedding 由 `DocumentProcessor` 记录，带 `DocumentId`、`AskId` 为空。多库/全局提问的 `KnowledgeBaseId` 为空，仪表盘单列「多库/全局」。

### 4.2 聚合

`src/KnowVault.Application/Dashboard/AiUsageAggregator.cs:21`：

- 今日 tokens / 费用、近 7 天总量、平均每次提问 token、`HasEstimated`
- 每日趋势按日期升序补 0
- 按库分组：`QuestionCount` 按 `AskId` 去重；名称为空时显示「多库/全局」，库已删除显示「已删除知识库」

`src/KnowVault.Application/Dashboard/DashboardAppService.cs:129` 把可见库范围内的最近 7 天记录交给聚合器，问答数字与用量数字同源。

### 4.3 价格配置

`Ai:Pricing:*`（CNY / 百万 token），默认值：

| 键 | 默认 |
|---|---|
| `DeepSeekInputPerMillion` / `DeepSeekOutputPerMillion` | 2 / 8 |
| `EmbeddingPerMillion` / `RerankPerMillion` | 0.07 / 0.07 |

## 5. 多库 / 全局链路

### 5.1 请求到检索

1. 前端 `chat` store 发送 `knowledgeBaseIds` 或 `allKnowledgeBases`
2. `src/KnowVault.Application/Qa/QaStreamService.cs:75` 调 `KnowledgeBaseScopeResolver.ResolveAsync`
3. `src/KnowVault.Application/KnowledgeBases/KnowledgeBaseScopeResolver.cs:65`：
   - `all` 与显式 ID 同时出现直接报错
   - `all` 取当前用户可访问 ID，默认库优先、其余按名称排序
   - 显式 ID 逐个校验 Viewer；任一无权或库不存在，整体抛 `无权访问以下知识库：…`，不静默过滤
   - 未指定时回落默认知识库（保持 P4 行为）
4. 解析结果同时给出 `Ids`、`PrimaryId`、`Names`；`QaStreamService` 用它构造 `RagRequest.KnowledgeBaseIds` 与引用库名

### 5.2 会话 scope

- `Conversation.UpdateScope(primaryId, ids, all)` 写入 `KnowledgeBaseScopeJson` / `ScopeAll`，主库用于会话列表归组
- 追问更换范围时同步更新，旧会话没有 scope 时前端回落单库
- 多库提问不使用单库自定义系统提示词与单库 TopK，使用全局配置

### 5.3 引用与前端恢复

- 引用 DTO 新增 `KnowledgeBaseName`；`QaStreamService.cs:136` 从 `scope.Names` 回填

## 7. 评估体系

### 7.1 资产

- 语料：`docs/eval/corpus/` 6 篇 RAG 主题 Markdown，单篇约 800–950 字符
- 金标：`docs/eval/golden-set.json` 30 题（关键词 10 / 语义 10 / 跨文档 5 / 不可回答 5）
- 锚点：题目的 `anchor` 必须是语料中的连续文本；开跑前 `AnchorResolver` 滚动 Qdrant 全量切片校验，失配直接报错

### 7.2 工具链路

1. `tools/KnowVault.Eval/Program.cs:24`：解析参数、读 `HttpApi.Host` 配置、构造真实依赖
2. `AnchorResolver.ResolveAsync`：校验锚点 → 解析为切片 ID
3. `tools/KnowVault.Eval/EvalRunner.cs:64`：按模式逐题调 `RagService`，记录命中、引用、回答、耗时与用量
4. `RankingMetrics` / `CitationParser`：Recall@5、MRR@10、nDCG@5、引用命中率与精确率
5. `EvaluationReportWriter`：写 Markdown + 同名 JSON

### 7.3 复现

```bash
dotnet run --project tools/KnowVault.Eval -- \
  --knowledge-base-id <评估知识库 GUID> \
  --modes vector,hybrid,hybrid-rewrite
```

前置条件与参数见 `docs/eval/README.md`。Key 只从 `Ai__SiliconFlowApiKey` / `Ai__DeepSeekApiKey` 环境变量读取，报告不写 Key。

### 7.4 本次结论

[2026-10-27 报告](eval/reports/2026-10-27-p5-eval.md)：

- 三组检索指标完全相同：Recall@5 0.900、MRR@10 0.847、nDCG@5 0.858
- 引用命中率 92.0%、精确率约 71.5%，三组持平
- 关键词题三组都排第 1，纯向量已是上限；跨文档 X01/X02 三组都未命中金标
- **结论：本语料上混合与改写没有可测增益，也没有回退**；小样本结论只用于判断方向

## 8. 验收与偏差记录

A1–A17 的逐项命令、结果与证据写在 `docs/plans/2026-10-27-knowvault-p5-mvp.md` §5。读代码时需要知道的三处偏差：

1. **A2 关键词增益未复现**：计划验收表期望「混合命中、纯向量不命中或排名更低」，实际三组在关键词题上都排第 1。没有为了通过验收去改语料或调权重；关键词分支的独立有效性由 `DenseWeight=0` 实测与 `Sparse_failure_falls_back_to_dense` 单测佐证。
2. **A6 与 T3 契约的措辞冲突**：验收表写「Started 可见原问题第一」，T3 详细规格写「Started 只返回变体」。实现按 T3：内部 `RewriteQueries` 原问题第一，`AnswerStreamAsync` 用 `Skip(1)`；前端只显示变体。
3. **T5 计价与实体基类**：计划示例价 0.5，实际按 2026-10-27 官网写入 0.07；`AiUsageRecord` 使用 `CreationAuditedAggregateRoot<Guid>`，不是计划里泛写的 `Entity`。

质量门禁（2026-10-27）：`dotnet build` 0 警告 0 错误；单测 109/109、集成测试 4/4；`npm run build` 通过（仅 chunk 体积提示）；`dotnet format ... IDE1006` 仅 3 条历史 `IMPORTS`，无新增违规。
