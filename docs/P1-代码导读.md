# KnowVault P1 代码导读（学习路线）

> 用途：在动手写 P2 之前，把 P1 的 **68 个 C# 文件 ≈ 2,800 行 + 13 个前端文件 ≈ 560 行**读明白。
> 读法建议：按 §2 的六个阶段顺序读，每阶段结束用「自检」问题确认理解；**§3 决策理由与 §4 踩坑记录的价值高于逐行读代码**。

## 1. 先建立全局心智模型

KnowVault 只有两条链路，其余一切都是为它们服务的。

### 写入链路（上传 → 变成向量）

```
POST /api/app/document/upload                          KnowVault.HttpApi/Controllers/DocumentUploadController.cs
  └─ DocumentAppService.UploadAsync                     Application/Documents/DocumentAppService.cs
       校验白名单/大小 → 扩展名推断来源类型 → 存 MinIO → Document 落库(Pending)
       → 事务提交后发消息（unitOfWork.OnCompleted）:110
  └─ (RabbitMQ: DocumentIngestRequested)               Ingest/Messaging/DocumentIngestRequested.cs
  └─ DocumentIngestConsumer.Consume                     Ingest/Messaging/DocumentIngestConsumer.cs:44
       自己开 UoW + 切租户（consumer 不在 HTTP 管线里）
  └─ DocumentProcessor.ProcessAsync                     Ingest/Processing/DocumentProcessor.cs:57
       MarkProcessing(:88)
       → MinIO 取回 → IDocumentParser 解析（带标题层级）
       → IDocumentChunker 切片（段落优先 + 字符容量 + 尾部重叠）
       → IEmbeddingService(SiliconFlow) 批量向量化（每批 ≤10，1024 维）
       → IVectorStore.UpsertAsync(Qdrant) 写点（payload 8 字段）(:137)
       → DocumentChunk 落库(:138) → MarkReady(:140)；任何异常 → MarkFailed(:76)
```

### 读取链路（提问 → 带引用的回答）

```
POST /api/app/qa/ask                                    Application/Qa/QaAppService.cs
  → 落 User Message
  → IRagService.AnswerAsync                             Ai/Rag/RagService.cs
       ① 问题向量化（IEmbeddingService）
       ② 检索（IVectorStore.SearchAsync：payload 过滤 tenantId + knowledgeBaseId，top-k≤8）
       ③ 组装 Prompt（RagPromptBuilder：编号片段 [1]《标题》· 标题路径 + 正文）
       ④ 生成（ILlmChatService → DeepSeek）
  → citations（score 降序）→ 落 Assistant Message(CitationsJson) → 返回
```

### 三层阅读主线

| 主线 | 含义 | 在 P1 里的体现 |
|---|---|---|
| **契约** | 接口与数据结构放哪、谁依赖谁 | `IVectorStore` / `IEmbeddingService` / `IDocumentStorage` / `IDocumentIngestPublisher` 全在 `KnowVault.Domain`，实现在 EF Core(基础设施) 与 Ai |
| **实现** | 每个契约的具体行为 | `QdrantVectorStore` / `MinioDocumentStorage` / `SiliconFlowEmbeddingService` / 5 个解析器 / `DocumentChunker` |
| **装配** | 谁把配置、DI、消息、编排串起来 | `KnowVaultAiModule` / `KnowVaultIngestModule` / `KnowVaultEntityFrameworkCoreModule` / 各 `appsettings.json` / `aspire/KnowVault.AppHost/Program.cs` |

## 2. 分阶段阅读路线

> **本节六个阶段的顺序，就是唯一权威的阅读顺序。**
> 它按「依赖关系」排列：先知道**数据长什么样**（阶段 1），再看**谁在写它**（阶段 3）、**谁在读它**（阶段 4），最后看**怎么装配起来**（阶段 2/5/6）。
>
> **不要按仓库目录树的顺序读**（`Domain → Application → EntityFrameworkCore → Ai → Ingest → HttpApi → Host`，或文件管理器里的字母序）：
> 那是「代码怎么组织」的顺序，不是「理解怎么发生」的顺序。按目录读，会在你还没见过一次完整上传之前，就先陷进某个类库的细节里。
> 换句话说：**"不要按目录顺序"指的是别按目录树读，而阶段编号本身就是推荐顺序**，两者不冲突。
>
> 时间紧张可以走**快线**：阶段 1 → 阶段 3 → 阶段 4（主干闭环），之后回补阶段 2（配置）、阶段 5（装配/前端）、阶段 6（测试）。
> 时间充裕就按 1→2→3→4→5→6 走完，阶段 2 只有 15 分钟，顺路读掉最省事。

## 3. 七个关键设计决策（为什么这么做）

| # | 决策 | 理由 | 替代方案与代价 |
|---|---|---|---|
| 1 | 接口在 Domain，实现在 EF Core / Ai | Ingest 要写向量、Ai 要读向量，但两者不能互相依赖；EF Core 项目在本项目里承担 Infrastructure 角色 | 新建 Infrastructure 项目（更纯，但 P1 改不动整个分层） |
| 2 | 单一 collection + payload 过滤 | 建 collection 有成本、运维要按知识库数增长；过滤式检索是 Qdrant 推荐用法 | 每知识库一个 collection（隔离强，但数量爆炸、跨库检索难） |
| 3 | `tenantId` 为 null 时写 `Guid.Empty` | **Qdrant 无法 match null**，单租户运行下过滤条件会恒不命中（这是真实坑） | payload 不写该字段（则多租户阶段要重刷全量数据） |
| 4 | 切片按**字符数**近似 token | 中文没有可靠 .NET tokenizer；引 tiktoken 类依赖对中英混排也不准 | 引 tokenizer（准确，但依赖重、中文仍不准） |
| 5 | MassTransit **进程内** consumer | 满足"走 RabbitMQ"的同时保留单进程可调试性；processor 与宿主解耦，P3 可平移成独立 Worker | 独立 Worker 进程（更"微服务"，但 P1 要多维护一套宿主/密钥/租户配置） |
| 6 | 上传用**显式 Controller** | DTO 里嵌 `IRemoteStreamContent` 时，ABP 动态 API 只声明 `application/json`，multipart 被拒 415 | 把文件作为方法参数（仍受动态 API 消费类型限制） |
| 7 | 发消息放 `unitOfWork.OnCompleted` | 消费者在事务提交前读不到新行（Postgres 隔离），会白跑并 ACK 掉消息 | 消费者端轮询等待（复杂、拖慢消费） |

## 4. P1 踩过的 8 个坑（价值最高的部分）

| # | 现象 | 根因 | 修法 | 通用教训 |
|---|---|---|---|---|
| 1 | 登录永远 `invalid_client` | DbMigrator **没有 launchSettings.json**，从仓库根 `dotnet run --project` 时工作目录停在根 → `appsettings.json` 根本没加载 → OpenIddict 客户端种子被 `if` 静默跳过（scope 不依赖配置所以照样建出来，掩盖了问题） | [DbMigrator/Program.cs](../src/KnowVault.DbMigrator/Program.cs) 加 `UseContentRoot(AppContext.BaseDirectory)` | "配置读不到"很少报错，只会**静默走默认值/跳过分支**；排查时先打印实际配置键 |
| 2 | 上传 405 | ABP 约定路由是**单数**：服务名去掉 `AppService` → `/api/app/document` | 前端改用 `/app/document` | 用 Swagger 核对真实路由，别按 REST 习惯猜复数 |
| 3 | 上传 415 | `[ApiController]` 把 DTO 参数推断为 `[FromBody]` → 只接受 JSON | 显式 Controller + `[Consumes("multipart/form-data")]` + `[FromForm]` | 文件上传这类"非 JSON 内容类型"的接口要显式声明消费类型 |
| 4 | Swagger 生成 500（路由冲突） | `[RemoteService(IsEnabled=false)]` 标在**接口**上不生效，动态端点照旧生成，与显式控制器同路由 | 该特性标在**实现类方法**上 | ABP 约定特性多作用于实现类；标错位置不会报错，只会在运行/生成期冲突 |
| 5 | 文档永远 Pending、日志「文档 xxx 不存在，跳过处理」 | **发消息早于事务提交**（写入链路的经典竞态） | `OnCompleted` 提交后发 + 找不到就抛错交给重试 + `UseMessageRetry` | 消息驱动系统里，"先落库再发消息"必须显式对齐事务边界 |
| 6 | `.env` 配了 Key 却不生效 | 只有 AppHost 读**进程环境变量**，没有任何代码读 `.env` | AppHost 增加 `LoadDotEnv()`（已存在的环境变量优先，不覆盖） | 配置来源要有唯一权威入口，并在文档里说明优先级 |
| 7 | Qdrant 检索搜不到（或编译期报错） | ① `Conditions.Match` 是数值/布尔匹配，GUID 以字符串落 payload 必须用 `MatchKeyword`；② 1.19 起 `SearchAsync` 已过时 | 改 `MatchKeyword` + `QueryAsync`（并显式开 `payloadSelector`） | 第三方 SDK 的"看起来对"的方法名要对着官方 API 文档核，别猜 |
| 8 | 问答 500：`Cannot resolve parameter 'ILlmChatService'` | 接口名 ≠ `I{类名}`，ABP 默认暴露约定没注册进容器 | `KnowVaultAiModule` 里显式 `AddTransient<I, Impl>()` | 依赖注约定时，命名即契约；不匹配就要显式注册 |

## 5. 动手实验（环境现成，边读边跑）

1. **看一次完整摄取流水**（理解写入链路的顺序）
   ```powershell
   Select-String -Path 'src\KnowVault.HttpApi.Host\Logs\logs.txt' -Pattern '摄入完成|SiliconFlow embedding|RECEIVE|Configured endpoint' | Select-Object -Last 20
   ```
2. **改切片参数看效果**：把 `appsettings.json` 的 `Ingest:ChunkSizeChars` 改成 300，重启 API，重传同一份 Markdown，对比 `AppDocumentChunks` 行数与 Qdrant points。
3. **直查向量与 payload**（理解契约）
   ```powershell
   curl.exe -s "http://localhost:6333/collections/knowvault_chunks"        # points_count
   '{"limit":2,"with_payload":true}' | Set-Content "$env:TEMP\s.json" -Encoding ASCII
   curl.exe -s -X POST "http://localhost:6333/collections/knowvault_chunks/points/scroll" -H "Content-Type: application/json" --data-binary "@$env:TEMP\s.json"
   ```
4. **调 top-k**：给 `POST /api/app/qa/ask` 加 `"topK": 8`，看 citations 数量变化（上限被 `Math.Clamp(...,1,8)` 限制）。
5. **资料外提问**：问一个文档里没有的问题，观察 system prompt 如何把它导向「根据现有资料无法回答该问题」。
6. **负向验证**：把 `.env` 的 `SILICONFLOW_API_KEY` 改错，重启 API 后上传 → 文档应落 `Failed` 且错误信息可见（顺带理解"失败也被持久化"的设计）。
7. **停掉 RabbitMQ 再上传**：`docker stop kv-rabbitmq`，上传一个文档，观察它停在 `Pending`（理解"状态推进完全依赖消息被消费"）。
8. **用 Swagger 摸 API**：打开 `https://localhost:44300/swagger`，对照 §1 的两条链路逐个试。

## 6. 需要补的背景知识（按需查，不必先学完）

| 主题 | 在本项目里的具体用法 | 建议关注点 |
|---|---|---|
| **ABP** | 模块化（`[DependsOn]`）、约定式 DI（`ITransientDependency`）、`IRepository<T>`、UoW（`IUnitOfWorkManager`）、动态 API（约定式 Controller 生成）、多租户过滤 | UoW 的事务边界、约定注册的"命名即契约" |
| **MassTransit** | `AddConsumer` / `UsingRabbitMq` / `ConfigureEndpoints` / `UseMessageRetry` / `Publish` | 消费端 UoW、重试与 error 队列、消息持久化 |
| **RAG 概念** | 切片（chunk/overlap）、embedding 维度、payload 过滤、top-k、Prompt 硬约束、引用溯源 | 为什么"资料不足要说不知道"比"答得像"更重要 |
| **Semantic Kernel** | `Kernel.CreateBuilder().AddOpenAIChatCompletion(...)`、`GetChatMessageContentAsync(system+user)` | 它只是 OpenAI 兼容调用的一层封装（P2 流式会用到） |
| **Qdrant** | collection/point/payload、`VectorParams(size, distance)`、`MatchKeyword` 过滤、Query API | 维度必须与 embedding 一致；过滤字段类型要与写入一致 |
