## 1. 先建立全局心智模型

P2 只做了一件事：**把 P1「一次性要完整段回答」改成「一边生成一边推给浏览器」，并给检索加了一道重排工序**。

### P2 新增的流式问答链路（★ 主线）

```
浏览器 ChatPanel.vue
  └─ stores/chat.js  ask()                                   前端状态机：占位气泡 → 事件累加 → 收尾
       └─ api/qaHub.js  connection.stream('Ask', input)      WebSocket 长连接（令牌走 query string）
            └─ SignalRAccessTokenMiddleware                  ★ 认证前把 ?access_token= 搬成 Authorization 头
                 └─ QaHub.AskAsync(input)                    HttpApi/Hubs/QaHub.cs:36
                      └─ IQaStreamService.AskStreamAsync     Application/Qa/QaStreamService.cs:54
                           ① 第一段 UoW：建/取会话 + 读历史 + 落用户消息   :62-71
                           ② IRagService.AnswerStreamAsync   Ai/Rag/RagService.cs:74
                                ├─ RetrieveAsync              :92  向量化 → 宽召回 20 → 重排 → 取 topK
                                └─ RagPromptBuilder.Build     :77  历史消息 + 资料片段 + 问题
                                      └─ ILlmChatService.CompleteStreamAsync  Chat/DeepSeekChatService.cs:31
                                           Semantic Kernel GetStreamingChatMessageContentsAsync  :45
                           ③ yield Started（会话 ID + 引用）      :92-97
                           ④ 逐条 yield Delta（正文增量）          :100-104
                           ⑤ 第二段 UoW：落 Assistant Message     :107-119
                           ⑥ yield Completed                     :121
```

### 与 P1 的关键差别

| 维度 | P1 | P2 |
|---|---|---|
| 生成 | `ILlmChatService.CompleteAsync`（一次性拿整段） | 只留 `CompleteStreamAsync`（`IAsyncEnumerable<string>`），**REST 入口改为把同一条流拼起来** |
| 检索 | 直接 `SearchAsync(topK)` | 宽召回 `RerankCandidateCount=20` → `qwen3-rerank` 精排 → 取 topK |
| 引用 `Score` | 向量余弦相似度 | 重排相关性分（0~1，**仅请求内相对可比**） |
| Prompt | system + 一条 user | system + **历史消息若干条** + 一条 user（历史里剥掉旧引用标记） |
| 前端 | 等整段回答后一次性渲染 | 逐字增长 + 「停止生成」+ SignalR 不可用时降级 REST |
| 知识库 | 只有列表 | 增改删（**删除仅限空库**） |

## 3. 十一个关键设计决策（为什么这么做）

| # | 决策 | 理由 | 替代方案与代价 |
|---|---|---|---|
| 1 | 流式与非流式**共用一条编排**（`AnswerAsync` 内部拼流） | 两套实现必然行为漂移（空回答检查、引用顺序、重排降级都得写两遍） | 各写一遍（简单，但改一处漏一处） |
| 2 | Hub 方法用 `Context.ConnectionAborted` | SignalR 会把 `CancellationToken` 参数当**客户端参数**，签名会被污染 | 自定义方法参数传取消（客户端要自己发，且断开时未必发得出来） |
| 3 | 令牌走 query string + 中间件搬运 | WebSocket 带不了自定义头；**OpenIddict 不读 query string**，所以必须自己搬 | 改 OpenIddict 事件（耦合更深、事件顺序难保证） |
| 4 | 两段显式 UoW（`requiresNew: true`） | `IAsyncEnumerable` 的真正工作发生在**枚举期间**，环境 UoW 在方法返回时就释放了 | 全程一个 UoW（生成期一直占连接，30 秒长事务） |
| 5 | 重排 **fail-open** | 重排是锦上添花，不能因为第三方抖动就让问答整体失败 | fail-fast（问题定位清晰，但可用性变差） |
| 6 | 宽召回 + 精排（20 → topK ≤ 8） | 候选数太少重排没有选择空间；太多白付重排费用（上限 `MaxCandidateCount=100`） | 直接 topK 重排（省一次调用，但重排无从发挥） |
| 7 | 引用 `Score` 语义改为「相关性 0~1」 | 重排分与余弦分**不可比**，混用会误导用户 | 同时保留两个分（要改契约与前端，收益不明） |
| 8 | 历史剥掉助手旧回答的 `[n]` | 否则模型会把上一轮的编号当成本轮来源，引用错乱 | 不剥（省一个正则，但引用溯源失真） |
| 9 | 助手消息在流**结束后**才落库 | 客户端断开 → 迭代器提前退出 → 半截回答根本不入库 | 边生成边写库（要额外做清理，且中断语义变模糊） |
| 10 | 删知识库只允许空库 | 文档删除要同时清 MinIO 对象与 Qdrant points（P3 才做），否则留下无主数据 | 级联删除（P2 内做不完，会留下脏数据） |
| 11 | 前端用 `n-tabs` 而不是路由 | 引 vue-router 要为两个视图加路由表、守卫、懒加载，收益只是 URL 好看 | 引 vue-router（改动面大，演示价值低） |

| # | 现象 | 根因 | 修法 | 通用教训 |
|---|---|---|---|---|
| 1 | 流式回答界面不更新 | Pinia state 里存的是**原始对象**，`push()` 之后再改这个本地引用，视图不会重新渲染 | 从 state 取回响应式引用：`const assistant = this.messages[this.messages.length - 1]` | 响应式系统的代理只包住「从 state 读出来」的那条路径 |
| 2 | SignalR 握手一直失败 | Vite 代理只配了 `target`，没开 `ws` → 只做普通 HTTP 代理 | [vite.config.js](../frontend/vite.config.js) `:23` 加 `ws: true` | WebSocket 的代理配置与普通 HTTP 不同，必须显式声明 |
| 3 | 带令牌仍然 401 | `openiddict.validation.aspnetcore 7.5.0` 的 DLL 里 `access_token` 字样命中 **0 次**（不读 query string） | 认证前用中间件把 query 里的令牌搬进 `Authorization` 头 | 第三方库的「默认行为」要实测确认，别按常识推断 |
| 4 | 知识库改名 405 | 前端把 ID 拼进 URL（`PUT /app/knowledge-base/{id}`），而 ABP 10.5 把 `UpdateAsync(输入DTO)` 映射为**不带 `{id}`** 的 PUT，ID 走请求体 | [knowledgeBases.js](../frontend/src/api/knowledgeBases.js) 改 URL；DTO 注释更正为实测结论 | **用 Swagger 核对真实路由**（与 P1 坑 2「别猜复数」同源） |
| 5 | 401 没有挑战头 | 直接改写状态码绕过了 Cookie 方案的 challenge，响应缺少 `WWW-Authenticate` | [KnowVaultHttpApiHostModule.cs](../src/KnowVault.HttpApi.Host/KnowVaultHttpApiHostModule.cs) `:205` 手动补 `WWWAuthenticate = "Bearer"` | 绕过框架默认流程时，要把它顺手做的事**列清单补回来** |
| 6 | 重排 403 `AccessDenied` | `gte-rerank` 已于 2026-05-30 下线（配置里的默认值过时了） | 换 `qwen3-rerank`（经典域名 `https://dashscope.aliyuncs.com/api/v1` 仍可用） | 第三方模型的默认值也要有「过期意识」，上线前冒烟 |
| 7 | 重排端点 404 | 想复用 `QwenBaseUrl`（OpenAI 兼容模式的 `/compatible-mode/v1`），但重排是 DashScope **原生**服务 | 独立配置项 `Ai:QwenRerankBaseUrl` | 「同一个厂商」不等于「同一个端点风格」 |
| 8 | 编译报 `CS8425` | `async IAsyncEnumerable` 方法的 `CancellationToken` 没标 `[EnumeratorCancellation]` | 每个流式方法都显式标注（`:34`、`:136`、`:56`） | 编译器警告常被忽略，但它是取消传播的唯一线索 |
| 9 | 取消后仍写库 / UoW 报错 | 把流式方法放进环境 UoW：ABP 的拦截器在方法**返回**时就结束 UoW，而流要到枚举时才产生 | 每次落库显式 `Begin(requiresNew: true)` + 类级 `<remarks>` 写明原因 | 「方法返回」不等于「工作结束」，迭代器/回调/后台任务都要重新审视事务边界 |
| 10 | `dotnet format ... --diagnostics IDE1006` 报一堆 `IMPORTS` | 该参数不生效，命令会顺带检查导入顺序 | 判据改为「**无新增违规**」（3 条历史 `IMPORTS` 是既有问题） | 校验命令本身也要验证，别把工具的噪音当成自己的错 |

## 5. 动手实验（环境现成，边读边跑）

1. **看一次完整的流**（理解三帧时序）
   ```powershell
   # 浏览器 http://localhost:5173 提问，F12 → Network → WS → /signalr/qa → Messages
   # 或用 Node 直连（需在 frontend 目录下装过依赖）：
   $env:NODE_PATH='frontend\node_modules'; $env:NODE_TLS_REJECT_UNAUTHORIZED='0'; node $env:TEMP\kv-stream.js
   ```
2. **关掉重排对比分数**：把环境变量 `Ai__RerankEnabled=false` 再起 API，问同一个问题，观察 citations 的分值区间从 0.9x/0.3x 变成 0.7x/0.7x、顺序也可能翻转（这就是「重排生效」的证据）。
3. **关掉历史**：`Ai__HistoryMaxMessages=0`，再问「它的预算是多少？」——指代会失效，回答会退化成「资料里没有明确说明」。
4. **看 fail-open**：把 `.env` 的 `QWEN_RERANK_MODEL` 改回 `gte-rerank`（会 403），提问 → 回答正常但日志里有 `重排失败，退回向量检索顺序`。
5. **验证半截回答不入库**：流式中途点「停止生成」，然后查库
   ```powershell
   docker exec -it kv-postgres psql -U root -d KnowVault -c "SELECT ""Role"", length(""Content"") FROM ""AppMessages"" ORDER BY ""CreationTime"" DESC LIMIT 5;"
   ```
   预期：只有用户消息，没有空的助手消息（`Role=1` 且长度为 0）。
6. **核对路由**：`https://localhost:44300/swagger` 找 `knowledge-base`，确认 `PUT` 不带 `{id}`、`DELETE` 带 `{id}`。
7. **反复删知识库**：新建 → 立刻删（应 204）；新建 → 传一个文档 → 等就绪 → 删（应 403 中文提示）；删默认库（应 403）。
8. **拔掉 Qdrant**：`docker stop kv-qdrant` 后提问，看错误如何一路冒到前端（理解异常传播路径），再 `docker start kv-qdrant` 恢复。

## 6. 需要补的背景知识（按需查）

| 主题 | 在本项目里的具体用法 | 建议关注点 |
|---|---|---|
| **SignalR** | `Hub` + `[HubMethodName]` + 服务端流 `IAsyncEnumerable`；JS 端 `connection.stream().subscribe()`；`Context.ConnectionAborted` | 传输协商（WebSocket/SSE/LongPolling）、流式调用的取消语义 |
| **`IAsyncEnumerable`** | 全链路流式：SK → `RagService` → `QaStreamService` → Hub → 前端 | `[EnumeratorCancellation]`、`WithCancellation`、`await foreach` |
| **ABP UoW** | `IUnitOfWorkManager.Begin(requiresNew: true)`、拦截器与迭代器的时序冲突 | 「事务边界在哪结束」在异步迭代场景里会变 |
| **ABP 动态 API** | `UpdateAsync` / `DeleteAsync` / `CreateAsync` 的约定路由、`[RemoteService(IsEnabled=false)]` | 约定优先于习惯；用 Swagger 核对 |
| **Semantic Kernel** | `GetStreamingChatMessageContentsAsync(history, ...)` 返回增量流 | 空帧、`AuthorRole` 映射 |
| **DashScope 重排** | `POST {base}/services/rerank/text-rerank/text-rerank`、`relevance_score` 0~1 | 分只在本请求内相对可比、`top_n` 限制 |
| **Vue/Pinia 响应式** | `watch` 监听数组末项 `content`、store 里存原始对象的下标引用问题 | `reactive` vs 原始对象、`nextTick` 与滚动 |

## 7. 与 P3 的衔接

P2 明确留给 P3 的东西（都在 `docs/plans/2026-10-14-knowvault-p2-mvp.md` §9.2「P2 不做」里）：

- **文档删除 + Qdrant points / MinIO 对象清理**（做完它，「删知识库」就能放开非空库限制）
- **会话列表与管理 API**、历史分页（现在只有「新会话」按钮，历史只在 Prompt 里用）
- **「重新处理」入口**（摄取中途被杀会停在 `Processing`/`Pending`）
- **RabbitMQ 消息持久化与重投**（重启会丢未消费消息）
- **Testcontainers 集成测试**（P2 仍只做纯函数/替身单测）
- **OpenTelemetry 全链路**（流式请求的跨度与耗时观测）
- **摄取进度实时推送**（现在前端仍是 2 秒轮询）
