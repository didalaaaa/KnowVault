# 重排模型与候选裁剪

向量相似不等于语义相关。向量检索把问题和切片分别编码，速度快但精度有限；重排模型把问题和候选切片放在一起编码，属于 cross-encoder，能捕捉两者之间的细粒度匹配关系，因此通常更准，也更慢。

KnowVault 使用 BAAI/bge-reranker-v2-m3 作为重排模型。它接收原问题与候选切片列表，为每条切片输出相关性分数，再按分数降序返回。重排只使用原问题，不使用改写变体，避免变体的措辞影响最终排序。

默认最多把 20 条候选送进重排，配置编号 KV-RERANK-20。候选来自混合检索的融合结果；候选太少会让重排没有发挥空间，候选太多会线性增加延迟和 token 成本。候选数至少要等于最终 topK。

重排服务返回每条候选的索引与分数，KnowVault 在本地按分数重排并截取 topK。服务端的 top_n 参数传全量候选，最终保留几条由应用层决定，这样 topK 可以随请求调整而不必重新调用模型。

重排是延迟最高的环节之一，成本按查询与候选文本的 token 数计算，编号 KV-RERANK-COST。问题越短、候选越少，成本越低；把候选数从 20 提到 100，延迟和费用都会明显上升，而召回质量未必同步提升。

重排失败时系统退回融合顺序并记录警告，不阻断问答。这个降级策略保证模型服务抖动时仍能给出基于向量检索的答案，只是排序质量下降。评估报告需要区分重排成功与降级两种情况。

重排分数只适合同一批候选内比较，不能跨问题比较。前端展示引用得分时保留三位小数，并注明它来自重排还是融合；两种分数的语义不同，不能混用。

最终 topK 默认是 5 条。重排候选数、topK 和评估指标需要一起看：Recall@5 衡量前 5 条是否覆盖金标，重排负责把真正相关的切片推进前 5 条。候选数足够大但重排质量差，Recall@5 仍然不会提升。
