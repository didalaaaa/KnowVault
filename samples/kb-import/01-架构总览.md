# KnowVault 架构总览

KnowVault（中文名「智库」）是一个基于 RAG 的多租户知识库系统，当前以单租户模式运行。它的定位一句话概括：你问，它从你的文档里找答案。用户上传私有文档，系统异步完成解析、切片、向量化并写入向量库，提问时按语义检索出最相关的片段，组装成提示词交给大模型生成回答，同时返回引用出处。

## 分层结构

后端采用 ABP VNext 的分层模板，整个解决方案由十二个项目组成，命名一律以 KnowVault 作为前缀。理解依赖方向是阅读代码的第一步：上层可以依赖下层，反向依赖被视为违规。

KnowVault.Domain.Shared 位于依赖链的最底部，存放跨层复用的共享枚举、常量与本地化资源。所有枚举类型名必须以 Enum 结尾，例如文档状态叫 DocumentStatusEnum，消息角色叫 MessageRoleEnum，一个 cs  文件只放一个枚举，文件名与类型名保持一致。

KnowVault.Domain 放实体、聚合根、领域事件与仓储接口，表结构从设计之初就带 TenantId 以预留多租户能力，主键统一使用 GUID。这一层不允许出现 EF Core 相关代码，也不允许出现 DTO。

KnowVault.Application.Contracts 定义应用服务契约与入参出参 DTO，接口名以 AppService 结尾，例如 IDocumentAppService 与 IKnowledgeBaseMemberAppService。

KnowVault.Application 是用例编排层，负责把上传、问答、知识库管理等业务串起来，这一层不写 SQL，也不直接操作向量库客户端。

KnowVault.EntityFrameworkCore 只做持久化，包含 PostgreSQL 的 DbContext 与 EF 迁移，同时承载 Qdrant 向量库和 MinIO 对象存储的访问实现；对应的接口 IVectorStore 与 IDocumentStorage 定义在 Domain 层。

KnowVault.Ai 是唯一允许出现 AI 相关逻辑的层，内含 Semantic Kernel 封装、提示词模板、RAG 编排、向量检索、重排与流式输出。遇到任何与检索增强生成有关的问题，应当先在这一层查找，不要散落到其它分层。

KnowVault.Ingest 负责文档解析与摄入，包含五种格式的解析器、切片器和消费 RabbitMQ 消息的 MassTransit 消费者。P1 阶段它以进程内消费者的形态运行在主宿主里，消费者与处理器保持宿主无关，因此 P3 之后可以整体拆分为独立 Worker 而不必改动业务逻辑。

KnowVault.HttpApi 提供 ABP 动态 API 自动生成的控制器，以及 P2 加入的 SignalR 集线器。KnowVault.HttpApi.Client 是给外部调用方使用的强类型 HttpClient 代理。KnowVault.HttpApi.Host 是主宿主，承载 OpenIddict 认证、健康检查与 Swagger，也是 Aspire 编排的入口。KnowVault.DbMigrator 是数据库迁移与种子数据的执行器。

## 命名空间约定

本项目强制使用扁平的根命名空间：命名空间一律只写项目名，不追加子目录层级。也就是说，文件 KnowVault.Ai 项目下的 Rag 子目录里的 RagService，它的命名空间是 KnowVault.Ai 而不是 KnowVault.Ai.Rag。同一项目内所有文件共用一个命名空间，与文件落在哪个子目录无关。禁止省略项目名退化到解决方案级的单一命名空间。

命名空间声明必须是块级写法，禁止使用文件级命名空间，否则触发 IDE0160 诊断。例外情况来自框架约定：EntityFrameworkCore 项目下的同名目录不参与命名空间拼接，EF 自动生成的 Migrations 目录固定使用 KnowVault.Migrations，属于生成物，不要手工改动其命名空间。

## 异步与取消令牌

凡是返回 Task、ValueTask 或 IAsyncEnumerable 的方法，签名里必须有 CancellationToken，并且要逐层透传，从 API 入口一路传到最底层的 EF 仓储、MinIO 与 Qdrant 客户端以及大模型的 HTTP 调用。参数名固定为 cancellationToken，位置排在最后一个参数。

入口型方法即应用服务和控制器 Action 不给默认值，因为 ABP 会从当前 HTTP 请求自动注入令牌，强制由入口传入是有意为之。Domain、Ai 与 EF 层的实现按仓库惯例给 default 值，便于测试与非 HTTP 场景调用。框架决定的签名是例外，包括模块生命周期方法、宿主服务的 StartAsync 与 StopAsync、健康检查、数据种子贡献者、MassTransit 消费者的 Consume 方法以及程序的 Main 入口，这些不要为了规范去改动它们。
