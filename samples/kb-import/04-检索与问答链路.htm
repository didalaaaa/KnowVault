KnowVault 检索与问答链路

端到端流程

一次提问的完整链路是：问题文本先经过 Qwen 向量化，然后带条件查询 Qdrant，过滤条件是租户标识加知识库标识，取回候选切片后交给重排服务精排，截取前若干条与原始问题一起组装成提示词，交给 DeepSeek 生成，最终返回答案与引用出处两部分。

宽召回加精排的重排策略

P2 把检索改成两段式。先用向量检索宽召回约 20 条候选，这个数量由配置项 Ai:RerankCandidateCount 控制，默认值就是 20，并且实际取值会被收敛到 TopK 与 100 之间。然后把全部候选交给重排服务端打分，最终返回条数在本地裁剪，由配置项 Ai:TopK 控制，默认值是 5，设计区间是 5 到 8 条。之所以不完全依赖服务端裁剪，是因为对端是否按其 top n 语义截断并不可靠。

重排服务使用阿里云 DashScope 的文本重排接口，经典域名的路径结尾是 text-rerank，模型名是 qwen3-rerank。这里有一个必须注意的点：重排接口不属于 OpenAI 兼容模式，必须单独配置 Ai 下的 QwenRerankBaseUrl，不能复用嵌入模型那个以兼容模式斜杠 v1 结尾的基础地址。旧的 gte-rerank 模型已于 2026 年 5 月 30 日下线，实测返回 403 拒绝访问，gte-rerank-v2 仍可用但不是默认值。

重排失败时的降级策略是放行而不是报错。当重排接口调用失败或返回空结果时，系统退回向量检索的原始顺序继续生成答案，这种行为在代码里被称为 fail-open。重排生效后，引用中的分数字段含义发生变化，从余弦相似度变成重排相关性分，取值在 0 到 1 之间，只在同一次请求内相对可比，跨请求比较没有意义。

提示词的硬性约束

系统提示词规定了三条纪律：只能根据提供的资料片段回答；资料不足时明确说不知道，不允许凭常识补全；回答必须标注来源。这三条是引用溯源功能的前提，也是测试时判断模型是否越界编造的依据。

多轮历史

P2 的多轮对话只做一件事：把最近 6 条历史消息注入提示词，由配置项 HistoryMaxMessages 控制，相当于三轮往返。P2 没有做会话列表侧边栏。历史消息以独立消息的形式注入，注入后最后一条用户消息仍然是资料片段加问题的组合。渲染前会剥掉助手旧回答里的方括号编号标记，避免编号污染上下文。系统提示词额外声明历史只用于理解指代关系，事实依据必须来自本次检索到的资料片段。

流式输出

打字机效果走 SignalR。服务端集线器路由是 /signalr/qa，方法名是 Ask，返回一个异步可枚举的事件流，每帧有三种类型：Started、Delta 与 Completed，前端用 connection 的 stream 方法消费。SignalR 的鉴权有一个坑：WebSocket 无法携带自定义请求头，浏览器端只能把访问令牌放在查询字符串里，而 OpenIddict 的验证处理不读取查询字符串，因此宿主在认证中间件之前插入一层专用中间件，只对集线器路径把查询串里的令牌搬运成 Bearer 认证头。

流式与工作单元存在冲突。ABP 的工作单元拦截器在方法返回时就结束了单元，而异步可枚举对象的真正工作发生在被枚举的过程中。因此流式编排服务不依赖环境工作单元，每次落库都显式开启一个新的单元，并且该服务标记为不生成动态 API 控制器。

两个问答入口

REST 问答接口与流式接口共用同一份检索、重排与落库实现，区别只在于 REST 入口把同一条流拼成整段文本再返回。大模型服务接口在 P2 之后只保留流式完成方法，非流式方法已删除。
